# 측정 기록

수치는 "측정 조건 → 기준 → 결과 → 결론" 순서로 남긴다. **기준은 측정 전에 먼저 적는다** (수치를 본 뒤에 기준을 잡으면 판단이 흔들린다).

## 1. 적 탐지 비용 (Phase 3 Step 4)

### 질문

적이 늘어나면 "플레이어를 발견했는가" 판정이 프레임 비용의 병목이 되는가?
병목이면 QuadTree(공간 분할)를 구현하고, 아니면 측정 수치와 미채택 사유를 기록한다.

### 비교 대상

| 방식 | 설명 |
| --- | --- |
| A. 거리 비교 (현재 구현) | 적마다 플레이어까지 XZ 제곱거리를 비교 (`EnemyController`) |
| B. `Physics.OverlapSphere` | 적마다 탐지 반경으로 `OverlapSphereNonAlloc` 호출 (계획서 기준 베이스라인) |

측정 구간은 Idle/Patrol 상태의 탐지 판정만이다 (추격·공격 중 거리 검사는 제외).

### 병목 판정 기준 (측정 전 확정 — 2026-11-17)

- 목표 프레임: 60 FPS = 프레임당 16.7 ms
- **적 30마리에서 탐지 비용이 프레임당 0.5 ms 이상** (프레임 예산의 약 3%), **또는**
- **적 100마리에서 프레임당 2.0 ms 이상** (프레임 예산의 약 12%)

둘 중 하나라도 넘으면 **병목으로 판단하고 QuadTree를 구현**한다. 둘 다 넘지 않으면 **미채택**하고 사유를 기록한다.

기준 설정 이유: Editor는 빌드보다 느리므로 Editor 수치로 판단해도 보수적이다. 모바일 타깃(성능 예산 Draw Call 50 이하)을 감안해 탐지가 프레임의 한 자릿수 % 이상을 먹으면 최적화 대상으로 본다.

### 측정 환경 · 방법

- 2026-11-17, Unity 6000.3.13f1 **Editor Play 모드** (빌드 아님), Windows 11, AMD Ryzen 5 5600X / 32GB
- 씬: `Dungeon_01` (바닥 + 벽 4개), 적은 `Enemy_Melee` 프리팹을 NavMesh 위 임의 지점에 생성해 모두 Idle/Patrol 상태 유지 (플레이어와 24m 이상 떨어짐 → 추격·공격 없음)
- 적 수 10 / 30 / 50 / 100, 조합마다 워밍업 60프레임 후 **300프레임 샘플링**
- 비용은 `ProfilerMarker` 값을 `ProfilerRecorder`로 읽은 프레임당 합계 (마커 자체 오버헤드가 포함되므로 상한에 가깝다)
  - A: `Enemy.Detection` (`EnemyController`의 탐지 판정)
  - B: `Bench.OverlapSphere` (`EnemyDetectionBenchmark`가 적마다 `OverlapSphereNonAlloc`, 마스크 `Player`)
- 도구: `Assets/Scripts/Debug/EnemyDetectionBenchmark.cs` (에디터/개발 빌드 전용), 원본 CSV는 이 문서 표와 동일

### 결과 (프레임당 탐지 비용)

| 적 수 | A. 거리 비교 | B. OverlapSphere | B / A |
| --- | --- | --- | --- |
| 10 | 0.010 ms | 0.020 ms | 2.0× |
| 30 | **0.026 ms** (프레임의 0.16%) | 0.059 ms (0.35%) | 2.3× |
| 50 | 0.035 ms | 0.087 ms | 2.5× |
| 100 | **0.062 ms** (프레임의 0.37%) | 0.187 ms (1.12%) | 3.0× |

(평균 기준. p95는 A 100마리 0.098 ms, B 100마리 0.270 ms. 최대값은 B 100마리 0.68 ms)

### 판정

- 기준 ① 30마리 0.5 ms 이상 → A 0.026 ms, B 0.059 ms — **미달** (기준의 5% / 12%)
- 기준 ② 100마리 2.0 ms 이상 → A 0.062 ms, B 0.187 ms — **미달** (기준의 3% / 9%)

**병목이 아니다 → QuadTree를 채택하지 않는다.**

### 미채택 사유와 해석

1. **현재 방식(A)은 이미 충분히 싸다.** 적당 약 0.6~1.0 µs, 100마리에서도 프레임의 0.4%다. 적이 늘어날수록 적당 비용이 오히려 줄어든다(캐시 워밍).
2. **계획서의 베이스라인(B, OverlapSphere)도 병목이 아니다.** 100마리에서 0.19 ms로 기준의 1/10 수준이다. 이 규모(던전 1개, 적 수십 마리)에서는 어느 쪽이든 선택 가능한 수준이고, 비용은 적 수에 선형으로 늘어난다(B는 약 1.9 µs/마리).
3. **QuadTree가 풀어 주는 문제와 이 게임의 질의가 맞지 않는다.** 탐지 대상이 플레이어 한 명이라 "플레이어 주변에 어떤 적이 있는가"를 질의 한 번으로 줄일 수는 있지만, 절약되는 것이 위 0.06 ms 수준이다. 트리 갱신(이동하는 적 100마리의 삽입/삭제)이 오히려 그보다 비쌀 수 있다. 적이 수백~수천 마리이거나 적끼리 이웃 질의(분리/군집)가 필요해지는 시점이 재검토 조건이다.
4. **이 측정이 알려 준 다음 병목 후보:** 적 100마리에서 Editor FPS가 260 → 125로 떨어지지만 탐지는 0.06 ms뿐이다. 프레임을 먹는 것은 탐지가 아니라 다른 곳(100개의 스키닝 메시·Animator·NavMeshAgent 갱신으로 추정, **아직 미확인**)이다. Phase 5의 "Profiler 병목 1건 측정 후 개선" 후보로 쓴다.

### 한계

- Editor 측정이다. 빌드(IL2CPP)와 실기기(모바일)에서는 절대값이 달라질 수 있다. 다만 기준 대비 여유가 10~30배라 결론이 뒤집힐 가능성은 낮다.
- 마커 오버헤드(호출당 수십 ns)가 포함되어 있어 A의 실제 비용은 표보다 더 낮다.
- 측정한 것은 Idle/Patrol 탐지뿐이다. 추격·공격 중 거리 검사, 경로 계산(NavMesh) 비용은 포함하지 않았다.

## 2. 전투 통합 검증 (Phase 3 Step 6)

`Dungeon_01` 한 씬에서 "플레이어 → 잡몹 5마리 → 보스" 전체 흐름을 돌렸다. 사람이 직접 한 플레이가 아니라
**플레이어의 실제 공격 경로**(`SkillHandler` → 애니메이션 이벤트 → `HitBox` → `EnemyHealth`)를 호출하는 봇으로 진행했다
(마우스 입력 시뮬레이션은 `Attack` 액션을 발동시키지 못해 입력 콜백 단계만 건너뛰었다).

### 환경

- 2026-11-17, Unity 6000.3.13f1 Editor Play 모드, AMD Ryzen 5 5600X
- 잡몹 5 (근접 3 + 원거리 2) + 보스 1, 플레이어 공격력 15, 봇은 공격마다 적 앞으로 이동해 1.6초 간격으로 공격, HP 40 미만이면 회복

### 결과

| 항목 | 결과 |
| --- | --- |
| 처치 | 6/6 — 처치 순서와 `OnEnemyDied` 순서 일치, 공격 45회, 총 72초 |
| `OnEnemyDied` / `OnBossDefeated` / `OnBossPhaseChanged` | 6 / 1 / 1 — 누락·중복 없음 |
| `OnHitLanded` | 47 (공격 45 + 보스 충격파 2) |
| 콘솔 오류 | 0 |

### 다수 동시 추격 성능

잡몹 5마리가 모두 추격·공격 상태인 24초 동안(8,849프레임):

| 평균 FPS | 중앙값 | p95 | p99 |
| --- | --- | --- | --- |
| 329 | 2.55 ms | 3.79 ms | 5.09 ms |

- 측정 첫 프레임의 2.9초는 측정용 `eval` 스크립트 컴파일이 만든 것이라 제외했다 (게임 코드가 아님).
- 이 규모에서는 프레임 예산(16.7 ms)을 크게 밑돈다. 적 100마리에서 FPS가 260 → 125로 떨어지던 현상(1번 측정)이 병목 후보로 남아 있다.

### 이 검증이 잡아낸 버그

- **플레이어의 공격이 적에게 데미지를 주지 못했다.** `WeaponHitBox`(트리거)와 적 콜라이더 모두 `Rigidbody`가 없어 `OnTriggerEnter`가 호출되지 않았다.
  판정 상자는 공격 첫 프레임부터 적 콜라이더와 겹쳐 있었지만 적 HP는 100%였다 (봇이 80번씩 공격해도 0마리 처치).
  kinematic `Rigidbody`를 추가하자 같은 공격이 HP 1.00 → 0.70으로 들어갔다.
- 플레이어를 `Player` 레이어로 옮긴 변경이 원인인지 의심해 확인했다: `Default` 레이어에 `Rigidbody` 없이도 똑같이 빗나갔으므로 **레이어 변경과 무관**하다.
- 이전 Phase에서 이 공격이 맞았다고 기록된 경위는 확인하지 못했다.

## 3. 씬 루프 통합 검증 (Phase 4 Step 5)

`TitleScene`에서 Play를 시작해 아래 순서로 진행하고, 씬이 바뀔 때마다 상태를 스냅샷으로 기록했다
(Unity 6000.3.13f1 Editor, 버튼은 `onClick.Invoke()`로 눌렀다 — 실제 마우스 입력은 시뮬레이션하지 않았다).

1. 타이틀 → 시작 → 던전 → 보스 처치 → 결과(VICTORY) → 타이틀
2. 타이틀 → 시작 → 던전 → 플레이어 사망 → 결과(DEFEAT) → 재도전 → 던전
3. 던전에서 히트스탑(`timeScale` 0) 도중 타이틀로 전환 → 시작 → 던전

| 점검 | 결과 (수정 후) |
| --- | --- |
| 던전 진입 4회 | 매번 정상, 콘솔 오류 0 |
| 결과 값 | VICTORY / 처치 1(보스 포함) / 사망 0, DEFEAT / 처치 0 / 누적 사망 1 |
| 이벤트 구독 수 (`OnEnemyDied`, `OnBossDefeated`, `OnPlayerDied`, `OnHitLanded`, `OnBossPhaseChanged`, `OnPlayerHPChanged`) | 던전 진입마다 8 / 1 / 2 / 3 / 2 / 1로 동일, 타이틀·결과에서는 모두 0 |
| ServiceLocator | 진입마다 `HitEffectPool`, `PlayerHealth`, `ProjectilePool` 재등록, 죽은 참조 없음, 영속 서비스(`SceneLoader`, `GameSession`)는 유지 |
| Singleton | `GameManager` 1개 유지 |
| `timeScale` | 히트스탑 중(0)에 전환해도 타이틀에서 1 |
| 커서 | 던전 Locked, 타이틀/결과 None |

수정 전에는 결과 씬에 `OnHitLanded`/`OnBossPhaseChanged` 구독이 2개씩 남았고, 던전 재진입 후 `CameraShakeManager`에서
`NullReferenceException`이 났으며, 보스 처치 시 처치 수가 0으로 표시됐다 (원인과 수정은 `docs/decisions.md`).

## 4. Profiler 병목 1건 — 적 수에 비례하는 드로우콜 (Phase 5)

### 병목 선정

"적 수가 늘 때 무엇이 가장 비싸지는가"를 추측하지 않고 데이터로 골랐다. Play 모드에서 Profiler가 등록한 시간 마커(약 2,300개)와
렌더 카운터를 적 0 / 50 / 100마리 조건에서 150프레임씩 샘플링해, 적을 늘릴 때 가장 크게 늘어나는 항목을 찾았다
(`ProfilerRecorder`, 적은 `Enemy_Melee`를 카메라 앞 영역에 배치해 모두 보이는 최악 조건, 플레이어와 10m 이상 떨어뜨려 추격·공격 없음).

| 적 수 (Before) | 50 | 100 |
| --- | --- | --- |
| FPS (Editor) | 137 | 94 |
| **드로우콜** | 873 | **1,705** (적 1마리당 약 16.4) |
| 배치 | 873 | 1,690 |
| 삼각형 | 313만 | 634만 |
| 보이는 스키닝 메시 | 204 | 404 (적 1마리당 4) |
| 메인 스레드 | 7.2 ms | 10.5 ms |
| `Shadows.DrawSRPBatcher` / `MeshSkinning.SkinOnGPU` / `Animators.Update` | 0.71 / 0.53 / 0.86 ms | 1.28 / 1.10 / 1.65 ms |

- 비용이 늘어나는 곳은 **렌더링**이다: 드로우콜, 그림자 패스, GPU 스키닝, `UpdateScene`. 탐지(0.06 ms)는 아니다.
- 적 1마리당 **스키닝 메시 4개**(몸·투구·방패·검)가 각각 메인 + 그림자 패스로 그려져 약 16개의 드로우콜을 만든다.
- 계획서의 모바일 예산은 "Draw Call 50 이하"인데, 적이 없어도 63이다(UI·벽·그림자 포함). 이 예산에 가장 크게 어긋나는 항목이라 선정했다.
- SRP Batcher는 이미 동작 중이라 SetPass 호출은 32~34로 일정하다. 문제는 상태 변경이 아니라 **드로우콜 수 자체**다.

### 원인 분석

`Paladin` 모델의 4개 `SkinnedMeshRenderer`는 **같은 재질(`Paladin_MAT`, 텍스처 없음)과 같은 69개 본 배열**을 쓴다.
재질이 같은데도 메시가 나뉘어 있어서 드로우콜만 4배가 되고 있었다. 스키닝 메시는 GPU 인스턴싱 대상이 아니라 배칭으로도 줄일 수 없다.
(참고: 검 하나가 삼각형의 약 88%(13,212 / 14,990)를 차지한다 — 다음 후보.)

### 개선: 메시 4개를 하나로 병합

- 정점·노멀·탄젠트·UV·본 가중치를 이어 붙이고 인덱스에 오프셋을 더해 **메시 1개 / 재질 1개 / 서브메시 1개**로 만들었다
  (`Paladin_Merged.mesh`, 정점 9,799 · 삼각형 14,990 — 합계 그대로).
- 병합 전에 바인드포즈를 검증했다. 방패 메시의 바인드포즈 46개가 첫 메시와 다르지만 **방패의 정점이 그 본들을 전혀 쓰지 않아**
  공통 바인드포즈를 써도 결과가 정확히 같다. (쓰는 정점이 있으면 병합을 중단하도록 검사를 넣었다.)
- 적 프리팹 3종(`Enemy_Melee`, `Enemy_Ranged`, `Boss`)의 `Model`을 병합 모델로 교체했다. 재질이 같아 외형은 그대로다.

### 결과 (같은 Play 세션에서 구/신 교대 측정 A-B-A-B, 적 100마리, 240프레임씩)

세션이 달라지면 FPS가 ±수십 % 흔들리는 것을 확인해서(같은 봇 플레이가 380 → 237 FPS), 구/신을 한 세션에서 번갈아 잰 값을 대표값으로 쓴다.

| 지표 | Before (메시 4개) | After (메시 1개) | 변화 |
| --- | --- | --- | --- |
| **드로우콜** | 1,433 (1,419 / 1,447) | **408** (404 / 412) | **−72%** |
| 배치 | 1,411 | 406 | −71% |
| 프레임 시간 (평균) | 8.07 ms | 6.82 ms | −15% |
| FPS (Editor) | 124 | 147 | +18% |
| 그림자 패스 (`Shadows.DrawSRPBatcher`) | 1.10 ms | 0.46 ms | −58% |
| GPU 스키닝 (`MeshSkinning.SkinOnGPU`) | 0.82 ms | 0.26 ms | −68% |
| 삼각형 (렌더된 수) | 540만 | 500만 | 모델의 삼각형 합계는 14,990 그대로. 7% 차이는 컬링 단위가 메시 4개 → 1개로 바뀐 영향으로 **추정**(미검증) |

세션을 달리한 첫 측정(적 100마리)에서도 같은 방향이었다: 드로우콜 1,705 → 503, 메인 스레드 10.5 → 8.0 ms, FPS 94 → 122.

- 적 1마리당 드로우콜 약 16.4 → 4.2 (메인 1 + 그림자 캐스케이드 ≈ 3).
- 회귀 확인: 전체 플레이 봇(잡몹 5 + 보스)이 이전과 동일한 결과(처치 6/6, `OnBossDefeated` 1, `OnBossPhaseChanged` 1,
  `OnHitLanded` 47)를 냈고, 선딜 틴트도 병합 메시에서 정상 동작한다(렌더러 1개, 색 `0.95 → 0.34`).

### 한계와 다음 후보

- Editor 측정이다. 모바일 실기기 수치는 아니다 (실기기 미확인).
- 적 100마리를 모두 화면에 둔 최악 조건이다. 실제 플레이에서는 화면 밖 적이 컬링되어 이득이 더 작을 수 있다.
- 남은 비용: 적 1마리당 약 4개 드로우콜(그림자 캐스케이드), 검의 고폴리(88%) → LOD/메시 단순화, 그림자 캐스케이드 수 조정.
  Animator 컬링 모드(`CullUpdateTransforms`)는 화면 밖 적에서만 효과가 있어 이번에는 적용하지 않았다.
- 원자료: `docs/data/draw-call-ab.csv`(교대 측정), `docs/data/profiler-scaling.csv`(0/50/100 스케일링).

## 5. Object Pool Before/After (Phase 5)

`ObjectPool<T>`가 실제로 쓰이는 두 프리팹(히트 이펙트, 적 투사체)을 같은 부하에서 `Instantiate/Destroy` 방식과 풀 방식으로
**번갈아 2회씩** 측정했다. 부하: 매 프레임 8개 생성, 40프레임 뒤 제거 → 600프레임 동안 4,800회 생성/제거.
풀은 최대 동시 생존 수(328개)만큼 미리 만들어 두었다 (로딩 시 1회 비용이라 측정 구간에서 제외). 도구: `Assets/Scripts/Debug/PoolBenchmark.cs`.

| 대상 | 방식 | 스폰/반환 CPU (프레임당) | 프레임 시간 평균 | 프레임 p95 | GC 할당 (600프레임) |
| --- | --- | --- | --- | --- | --- |
| HitEffect | Instantiate/Destroy | **1,290 µs** | 8.83 ms | 12.3 ms | 11,979 KB |
| HitEffect | ObjectPool | **135 µs** (−90%) | 5.69 ms (−36%) | 8.5 ms | 6,562 KB |
| EnemyProjectile | Instantiate/Destroy | 556 µs | 8.07 ms | 12.1 ms | 11,646 KB |
| EnemyProjectile | ObjectPool | 309 µs (−44%) | 5.80 ms (−28%) | 9.1 ms | 6,575 KB |

(각 값은 2회 평균. 원자료 `docs/data/object-pool.csv`)

- **GC 할당:** 풀 쪽의 약 6,560 KB는 에디터 자체의 기본 할당(프레임당 약 11 KB × 600)과 같은 수준이라 풀이 추가로 만드는 할당은
  거의 없다. `Instantiate/Destroy`는 그 위에 **약 5,070~5,420 KB(5.0~5.3 MB)를 더** 할당한다(인스턴스당 약 1.1 KB). 단위는 KB = 1,024 B.
- **투사체의 개선폭이 작은 이유:** 풀에서 꺼낼 때 `SetActive(true)`로 콜라이더와 Rigidbody를 켜는 비용이 남는다.
- **측정한 구간에서는 GC가 한 번도 발동하지 않았다**(gen0 = 0). 그래서 "GC 횟수가 줄었다"고는 주장하지 않는다. 할당량 감소로만 말한다.
- 프레임 시간 개선에는 스폰 CPU 절감 외에 Destroy 시점의 정리 비용 제거도 섞여 있다.
- 한계: Editor 측정이고, 실제 게임의 히트 빈도(수 회/초)는 이 부하(초당 약 480회)보다 훨씬 낮다. 부하를 크게 잡아 차이를 드러낸 것이다.

## 6. 결과 화면 해상도 확인

`ResultScene`을 Play 모드로 띄우고 Game 뷰 해상도를 바꿔 가며, 모든 UI 요소(`Graphic`) 8개의 화면 좌표 범위가 화면 안에 들어오는지 계산했다
(Canvas Scaler: Scale With Screen Size, 기준 1920×1080, Match 0.5).

| 해상도 | 비율 | 스케일 | 요소 범위가 화면 안 |
| --- | --- | --- | --- |
| 1920×1080 | 16:9 | 1.00 | ✅ |
| 1280×720 | 16:9 | 0.67 | ✅ |
| 2560×1080 | 21:9 | 1.15 | ✅ |
| 2340×1080 | 19.5:9 (폰) | 1.10 | ✅ |
| 1024×768 | 4:3 (태블릿) | 0.62 | ✅ |
| 1080×1920 | 9:16 (세로) | 1.00 | 박스 기준 ❌ (x −160 ~ 1240) → 스크린샷에서는 **글자가 잘리지 않음** |

- 세로 모드에서 ❌인 것은 보이지 않는 텍스트 박스(폭 1400)가 화면 폭(1080)보다 넓기 때문이고, 실제 글자와 버튼은 전부 화면 안에 보인다(`docs/images/result-portrait.png`).
- 어차피 가로 전용 게임이라 화면 방향을 **가로 전용으로 고정**했다 (`allowedAutorotateToPortrait` 해제). 세로 대응은 하지 않았다.
- Game 뷰 크기를 임시로 추가해 측정하고 측정 후 모두 제거했다. 실제 기기의 노치/펀치홀은 `SafeAreaFitter` 적용 여부만 확인했고 기기에서 확인하지는 못했다.

## 7. 모바일 온스크린 컨트롤 검증

`OnScreenStick`/`OnScreenButton`을 `PlayerInputActions`가 이미 쓰는 게임패드 경로에 매핑했다. Play 모드에서 값을 직접 주입해 확인했다
(실제 터치 입력이 아니라 `OnScreenControl.SendValueToControl`로 값을 보냄).

| 입력 | 결과 |
| --- | --- |
| 데스크톱(터치 아님) | 컨트롤 숨김, 가상 게임패드 장치 생성 안 됨 |
| 왼쪽 스틱 (0, 1) | 1.5초에 5.24 m 이동, Speed 파라미터 1.0 — **입력 처리 코드 수정 없음** |
| 공격 버튼 | `Slash 1` 재생, 히트박스 활성화 |
| 오른쪽 스틱 (1, 0) | 처음에는 **카메라가 돌지 않음** → 원인: Cinemachine이 읽는 `Look` 액션에 `<Mouse>/delta`만 있었음 |

- 카메라 회전만은 입력 에셋을 고쳐야 했다: `Look`에 `<Gamepad>/rightStick`을 `ScaleVector2(10,10)`으로 추가 (마우스 델타는 픽셀 단위, 스틱은 ±1이라 배율이 필요).
  수정 후 1초에 47.9° 회전(마우스와 비슷한 체감 속도).
- 처음 배치에서 `JMP` 버튼이 기존 스킬 쿨타임 아이콘과 겹쳐 오른쪽 컨트롤을 위로 올렸다.
- **한계:** 실제 터치 기기에서 확인하지 못했다. 멀티터치(이동하면서 공격) 동작, 터치 영역 크기, 손가락에 가려지는 정도는 미확인이다.

# 측정 기록

수치는 "측정 조건 → 기준 → 결과 → 결론" 순서로 남긴다. **기준은 측정 전에 먼저 적는다** (수치를 본 뒤에 기준을 잡으면 판단이 흔들린다).

## 1. 적 탐지 비용 (Phase 3 Step 4)

### 질문

적이 늘어나면 "플레이어를 발견했는가" 판정이 프레임 비용의 병목이 되는가?
병목이면 QuadTree(공간 분할)를 구현하고, 아니면 측정 수치와 미채택 사유를 기록한다.

### 비교 대상

| 방식 | 설명 |
| --- | --- |
| A. 거리 비교 (현재 구현) | 적마다 플레이어까지 XZ 제곱거리를 비교 (`EnemyController`) |
| B. `Physics.OverlapSphere` | 적마다 탐지 반경으로 `OverlapSphereNonAlloc` 호출 (계획서 기준 베이스라인) |

측정 구간은 Idle/Patrol 상태의 탐지 판정만이다 (추격·공격 중 거리 검사는 제외).

### 병목 판정 기준 (측정 전 확정 — 2026-11-17)

- 목표 프레임: 60 FPS = 프레임당 16.7 ms
- **적 30마리에서 탐지 비용이 프레임당 0.5 ms 이상** (프레임 예산의 약 3%), **또는**
- **적 100마리에서 프레임당 2.0 ms 이상** (프레임 예산의 약 12%)

둘 중 하나라도 넘으면 **병목으로 판단하고 QuadTree를 구현**한다. 둘 다 넘지 않으면 **미채택**하고 사유를 기록한다.

기준 설정 이유: Editor는 빌드보다 느리므로 Editor 수치로 판단해도 보수적이다. 모바일 타깃(성능 예산 Draw Call 50 이하)을 감안해 탐지가 프레임의 한 자릿수 % 이상을 먹으면 최적화 대상으로 본다.

### 측정 환경 · 방법

- 2026-11-17, Unity 6000.3.13f1 **Editor Play 모드** (빌드 아님), Windows 11, AMD Ryzen 5 5600X / 32GB
- 씬: `Dungeon_01` (바닥 + 벽 4개), 적은 `Enemy_Melee` 프리팹을 NavMesh 위 임의 지점에 생성해 모두 Idle/Patrol 상태 유지 (플레이어와 24m 이상 떨어짐 → 추격·공격 없음)
- 적 수 10 / 30 / 50 / 100, 조합마다 워밍업 60프레임 후 **300프레임 샘플링**
- 비용은 `ProfilerMarker` 값을 `ProfilerRecorder`로 읽은 프레임당 합계 (마커 자체 오버헤드가 포함되므로 상한에 가깝다)
  - A: `Enemy.Detection` (`EnemyController`의 탐지 판정)
  - B: `Bench.OverlapSphere` (`EnemyDetectionBenchmark`가 적마다 `OverlapSphereNonAlloc`, 마스크 `Player`)
- 도구: `Assets/Scripts/Debug/EnemyDetectionBenchmark.cs` (에디터/개발 빌드 전용), 원본 CSV는 이 문서 표와 동일

### 결과 (프레임당 탐지 비용)

| 적 수 | A. 거리 비교 | B. OverlapSphere | B / A |
| --- | --- | --- | --- |
| 10 | 0.010 ms | 0.020 ms | 2.0× |
| 30 | **0.026 ms** (프레임의 0.16%) | 0.059 ms (0.35%) | 2.3× |
| 50 | 0.035 ms | 0.087 ms | 2.5× |
| 100 | **0.062 ms** (프레임의 0.37%) | 0.187 ms (1.12%) | 3.0× |

(평균 기준. p95는 A 100마리 0.098 ms, B 100마리 0.270 ms. 최대값은 B 100마리 0.68 ms)

### 판정

- 기준 ① 30마리 0.5 ms 이상 → A 0.026 ms, B 0.059 ms — **미달** (기준의 5% / 12%)
- 기준 ② 100마리 2.0 ms 이상 → A 0.062 ms, B 0.187 ms — **미달** (기준의 3% / 9%)

**병목이 아니다 → QuadTree를 채택하지 않는다.**

### 미채택 사유와 해석

1. **현재 방식(A)은 이미 충분히 싸다.** 적당 약 0.6~1.0 µs, 100마리에서도 프레임의 0.4%다. 적이 늘어날수록 적당 비용이 오히려 줄어든다(캐시 워밍).
2. **계획서의 베이스라인(B, OverlapSphere)도 병목이 아니다.** 100마리에서 0.19 ms로 기준의 1/10 수준이다. 이 규모(던전 1개, 적 수십 마리)에서는 어느 쪽이든 선택 가능한 수준이고, 비용은 적 수에 선형으로 늘어난다(B는 약 1.9 µs/마리).
3. **QuadTree가 풀어 주는 문제와 이 게임의 질의가 맞지 않는다.** 탐지 대상이 플레이어 한 명이라 "플레이어 주변에 어떤 적이 있는가"를 질의 한 번으로 줄일 수는 있지만, 절약되는 것이 위 0.06 ms 수준이다. 트리 갱신(이동하는 적 100마리의 삽입/삭제)이 오히려 그보다 비쌀 수 있다. 적이 수백~수천 마리이거나 적끼리 이웃 질의(분리/군집)가 필요해지는 시점이 재검토 조건이다.
4. **이 측정이 알려 준 다음 병목 후보:** 적 100마리에서 Editor FPS가 260 → 125로 떨어지지만 탐지는 0.06 ms뿐이다. 프레임을 먹는 것은 탐지가 아니라 다른 곳(100개의 스키닝 메시·Animator·NavMeshAgent 갱신으로 추정, **아직 미확인**)이다. Phase 5의 "Profiler 병목 1건 측정 후 개선" 후보로 쓴다.

### 한계

- Editor 측정이다. 빌드(IL2CPP)와 실기기(모바일)에서는 절대값이 달라질 수 있다. 다만 기준 대비 여유가 10~30배라 결론이 뒤집힐 가능성은 낮다.
- 마커 오버헤드(호출당 수십 ns)가 포함되어 있어 A의 실제 비용은 표보다 더 낮다.
- 측정한 것은 Idle/Patrol 탐지뿐이다. 추격·공격 중 거리 검사, 경로 계산(NavMesh) 비용은 포함하지 않았다.

## 2. 전투 통합 검증 (Phase 3 Step 6)

`Dungeon_01` 한 씬에서 "플레이어 → 잡몹 5마리 → 보스" 전체 흐름을 돌렸다. 사람이 직접 한 플레이가 아니라
**플레이어의 실제 공격 경로**(`SkillHandler` → 애니메이션 이벤트 → `HitBox` → `EnemyHealth`)를 호출하는 봇으로 진행했다
(마우스 입력 시뮬레이션은 `Attack` 액션을 발동시키지 못해 입력 콜백 단계만 건너뛰었다).

### 환경

- 2026-11-17, Unity 6000.3.13f1 Editor Play 모드, AMD Ryzen 5 5600X
- 잡몹 5 (근접 3 + 원거리 2) + 보스 1, 플레이어 공격력 15, 봇은 공격마다 적 앞으로 이동해 1.6초 간격으로 공격, HP 40 미만이면 회복

### 결과

| 항목 | 결과 |
| --- | --- |
| 처치 | 6/6 — 처치 순서와 `OnEnemyDied` 순서 일치, 공격 45회, 총 72초 |
| `OnEnemyDied` / `OnBossDefeated` / `OnBossPhaseChanged` | 6 / 1 / 1 — 누락·중복 없음 |
| `OnHitLanded` | 47 (공격 45 + 보스 충격파 2) |
| 콘솔 오류 | 0 |

### 다수 동시 추격 성능

잡몹 5마리가 모두 추격·공격 상태인 24초 동안(8,849프레임):

| 평균 FPS | 중앙값 | p95 | p99 |
| --- | --- | --- | --- |
| 329 | 2.55 ms | 3.79 ms | 5.09 ms |

- 측정 첫 프레임의 2.9초는 측정용 `eval` 스크립트 컴파일이 만든 것이라 제외했다 (게임 코드가 아님).
- 이 규모에서는 프레임 예산(16.7 ms)을 크게 밑돈다. 적 100마리에서 FPS가 260 → 125로 떨어지던 현상(1번 측정)이 병목 후보로 남아 있다.

### 이 검증이 잡아낸 버그

- **플레이어의 공격이 적에게 데미지를 주지 못했다.** `WeaponHitBox`(트리거)와 적 콜라이더 모두 `Rigidbody`가 없어 `OnTriggerEnter`가 호출되지 않았다.
  판정 상자는 공격 첫 프레임부터 적 콜라이더와 겹쳐 있었지만 적 HP는 100%였다 (봇이 80번씩 공격해도 0마리 처치).
  kinematic `Rigidbody`를 추가하자 같은 공격이 HP 1.00 → 0.70으로 들어갔다.
- 플레이어를 `Player` 레이어로 옮긴 변경이 원인인지 의심해 확인했다: `Default` 레이어에 `Rigidbody` 없이도 똑같이 빗나갔으므로 **레이어 변경과 무관**하다.
- 이전 Phase에서 이 공격이 맞았다고 기록된 경위는 확인하지 못했다.

## 3. 씬 루프 통합 검증 (Phase 4 Step 5)

`TitleScene`에서 Play를 시작해 아래 순서로 진행하고, 씬이 바뀔 때마다 상태를 스냅샷으로 기록했다
(Unity 6000.3.13f1 Editor, 버튼은 `onClick.Invoke()`로 눌렀다 — 실제 마우스 입력은 시뮬레이션하지 않았다).

1. 타이틀 → 시작 → 던전 → 보스 처치 → 결과(VICTORY) → 타이틀
2. 타이틀 → 시작 → 던전 → 플레이어 사망 → 결과(DEFEAT) → 재도전 → 던전
3. 던전에서 히트스탑(`timeScale` 0) 도중 타이틀로 전환 → 시작 → 던전

| 점검 | 결과 (수정 후) |
| --- | --- |
| 던전 진입 4회 | 매번 정상, 콘솔 오류 0 |
| 결과 값 | VICTORY / 처치 1(보스 포함) / 사망 0, DEFEAT / 처치 0 / 누적 사망 1 |
| 이벤트 구독 수 (`OnEnemyDied`, `OnBossDefeated`, `OnPlayerDied`, `OnHitLanded`, `OnBossPhaseChanged`, `OnPlayerHPChanged`) | 던전 진입마다 8 / 1 / 2 / 3 / 2 / 1로 동일, 타이틀·결과에서는 모두 0 |
| ServiceLocator | 진입마다 `HitEffectPool`, `PlayerHealth`, `ProjectilePool` 재등록, 죽은 참조 없음, 영속 서비스(`SceneLoader`, `GameSession`)는 유지 |
| Singleton | `GameManager` 1개 유지 |
| `timeScale` | 히트스탑 중(0)에 전환해도 타이틀에서 1 |
| 커서 | 던전 Locked, 타이틀/결과 None |

수정 전에는 결과 씬에 `OnHitLanded`/`OnBossPhaseChanged` 구독이 2개씩 남았고, 던전 재진입 후 `CameraShakeManager`에서
`NullReferenceException`이 났으며, 보스 처치 시 처치 수가 0으로 표시됐다 (원인과 수정은 `docs/decisions.md`).

# 포트폴리오 PDF — 프로젝트 2 슬라이드 초안

기존 PDF의 "프로젝트 2" 부분을 갱신하기 위한 슬라이드별 내용이다 (Object Pool, 적 AI, 보스, 측정 결과 추가).
모든 수치는 `docs/measurements.md` / `docs/data/`의 실측값이며, **Unity Editor Play 모드 측정이고 실기기 수치는 없다**는 점을 슬라이드에도 한 줄로 밝혀 둔다.
이미지는 `docs/images/`에 있다.

---

## 슬라이드 1 — 프로젝트 개요

**제목:** Unity 3인칭 액션 RPG — 타이틀 → 던전 → 보스 → 결과 한 판 루프

- 1인 개발, Unity 6 · URP · C# · UniTask · Cinemachine · New Input System
- 잡몹 5마리(근접 3 + 원거리 2) → 2페이즈 보스 → 결과 화면(VICTORY / DEFEAT)
- 설계 판단과 측정을 코드와 같은 비중으로 문서화 (`docs/decisions.md`, `docs/measurements.md`)
- **넣을 것:** 한 판 흐름 다이어그램(README의 Mermaid), 플레이 화면 1장

## 슬라이드 2 — 아키텍처와 패턴

**핵심 메시지:** 결합도를 낮추는 패턴을 "필요한 곳에만" 적용했다.

- Observer(EventBus) · Service Locator · Command · FSM · Strategy(+Template Method) · Object Pool · ScriptableObject
- Singleton은 `GameManager` 1개. 나머지는 Service Locator로 풀고, **씬 소속 서비스는 `OnDestroy`에서 해제**
- **넣을 것:** README의 아키텍처 다이어그램

## 슬라이드 3 — 적 AI: FSM + Strategy

**핵심 메시지:** 적 종류를 코드 수정 없이 바꿔 끼우고, 반응할 수 있는 공격 선딜을 구조로 보장했다.

- FSM: Idle / Patrol / Chase / Attack / Hit / Dead, NavMeshAgent 순찰·추격, 거리는 SO 주입
- Strategy: `IEnemyBehavior`를 SO로 구현 → 근접 / 원거리 / 범위 / 보스 패턴 (런타임 교체 확인)
- Template Method: 선딜 → 타격 → 후딜 골격 고정, 구현체는 `Strike()`만
- 선딜 시간은 **애니메이션 클립의 손 속도 최대 시점을 샘플링**해 결정 (감이 아니라 데이터)
- 타격 순간에 다시 판정 → 선딜 중 물러나면 빗나감(HP 불변 확인), 선딜 중 맞으면 공격 중단
- **넣을 것:** `enemy-windup-telegraph.png` (선딜 중 붉게 물든 적)

## 슬라이드 4 — 보스

**핵심 메시지:** 일반 적 FSM을 상속해 재사용하고, 페이즈는 데이터로 정의했다.

- `BossController : EnemyController` — 공격/사거리/이동 속도만 `virtual`로 교체
- `BossData` SO: HP 임계값 · 패턴 목록 · 간격 · 이동 속도 배율. 페이즈 2(HP 50% 이하)에서 충격파 추가, 이동 ×1.3
- 패턴 체이닝(UniTask `await`) — 대상이 닿지 않는 패턴은 건너뜀. 취소 토큰으로 사망 시 체인 전체 중단
- 페이즈 전환은 EventBus 이벤트 하나로 히트스탑(0.25 s) + 카메라 쉐이크(일반 타격의 약 3배) — 매니저는 보스를 모름
- **넣을 것:** `boss-shockwave-telegraph.png` (바닥 범위 원이 차오르는 충격파 선딜)

## 슬라이드 5 — Object Pool

**핵심 메시지:** 같은 부하에서 `Instantiate/Destroy`와 풀을 번갈아 측정했다.

| 대상 (4,800회 생성/제거) | 스폰/반환 CPU | 프레임 시간 | 추가 GC 할당 |
| --- | --- | --- | --- |
| HitEffect — Instantiate/Destroy | 1,290 µs | 8.83 ms | 약 5.3 MB |
| HitEffect — ObjectPool | **135 µs (−90%)** | 5.69 ms | ≈ 0 |
| EnemyProjectile — Instantiate/Destroy | 556 µs | 8.07 ms | 약 5.0 MB |
| EnemyProjectile — ObjectPool | **309 µs (−44%)** | 5.80 ms | ≈ 0 |

- 투사체의 개선폭이 작은 이유: 활성화(`SetActive`)로 콜라이더/Rigidbody를 켜는 비용이 남음
- 측정 구간에서 GC가 발동하지 않아 "GC 횟수 감소"는 주장하지 않음 (할당량으로만 말함)
- **넣을 것:** 위 표를 막대 그래프로 (스폰 CPU 기준)

## 슬라이드 6 — Profiler로 찾은 병목 1건: 드로우콜

**핵심 메시지:** 추측하지 않고 마커 2,300여 개를 비교해 병목을 골랐다.

- 적 0/50/100마리에서 가장 크게 늘어나는 항목 = **드로우콜**(적 1마리당 약 16개). 탐지(0.06 ms)가 아니었음
- 원인: 4개 스키닝 메시(몸·투구·방패·검)가 **같은 재질·같은 69개 본 배열**인데 나뉘어 있었음
- 개선: 메시 1개로 병합 (바인드포즈가 다른 메시는 "그 본을 쓰는 정점이 없음"을 검증한 뒤 병합)

| 적 100마리 (같은 세션 교대 측정 A-B-A-B) | Before | After | 변화 |
| --- | --- | --- | --- |
| 드로우콜 | 1,433 | **408** | **−72%** |
| 프레임 시간 | 8.07 ms | 6.82 ms | −15% |
| FPS | 124 | 147 | +18% |

- 처음에 세션을 달리해 잰 개선폭(+30%)이 세션 간 변동에 흔들리는 것을 발견해 교대 측정으로 다시 재고 **작은 값을 대표로 채택**
- **넣을 것:** Before/After 드로우콜 막대 그래프

## 슬라이드 7 — 측정 기반 판단: QuadTree 미채택

**핵심 메시지:** 기준을 먼저 정하고 쟀고, 병목이 아니면 만들지 않았다.

- 병목 기준(30마리 0.5 ms / 100마리 2.0 ms)을 **측정 전에 커밋**
- 100마리에서 현재 방식 0.062 ms, `OverlapSphere` 0.187 ms → 기준의 3% / 9%
- 결론: QuadTree 미채택. 재검토 조건(적 수백~수천 마리, 적끼리 이웃 질의)까지 기록

## 슬라이드 8 — 통합 검증이 잡아낸 버그

**핵심 메시지:** 단위 호출 테스트를 통과해도 실제 경로에서는 깨져 있었다.

1. **플레이어의 공격이 적에게 한 번도 맞지 않았다** — 트리거 판정에 `Rigidbody`가 없어 `OnTriggerEnter` 미호출.
   판정 상자가 적과 겹쳐 있는데도 HP 100%. 직전에 바꾼 레이어 변경이 원인인지 되돌려 확인해 배제하고 원인을 특정
2. **씬 재진입 후 카메라 쉐이크가 예외** — `DontDestroyOnLoad` 오브젝트에 씬 종속 매니저가 붙어 있어 파괴된 참조를 잡고 있었음.
   씬 소속 오브젝트로 분리
3. **보스 처치 시 처치 수 0** — 이벤트 발행 순서 문제. 결과 생성을 한 프레임 뒤로 이동
